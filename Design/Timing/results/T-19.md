# 🧪 T-19 — `htm` mechanics: tap → sticky mod, hold with captured key

> Rig R1 (synthetic 3×4), native_posix_64, `--no-rt`. 4 cases, all built and ran first time (`PASS` after auto-accept, and `PASS` again on a second run against the snapshot).
> `t` = physical press of the `htm` key (pos 5) = **62 ms absolute** in every case. Every relative time below is `abs − 62`.

## 🎯 Verdict: **deviates** (the mechanics hold, three literal spec lines do not)

- ✅ **E-110 / MODEL §(e) confirmed.** `&kp LCTRL` goes down when the hold-tap is created (hold-while-undecided). `skm` runs only on a tap, and the modifier byte stays `0x01` from then until the key that uses it is released.
- ✅ **Hold with a captured key.** C is delivered at **t+131** by the timer HOLD, with ctrl down. This matches the spec to the millisecond.
- ❌ **Three spec lines contradict the log.**
  - ⏱️ `0xE0↓` comes at **t+19**, not "at press". Pos 5 sits in two combos on layer 4 (S16 and Q18), so the combo engine holds it 18 ms before the hold-tap exists.
  - 📜 **There is a `kp_released 0xE0` line at the end of the tap** (t+51). It is the refcount going 2→1, so the modifier byte does not change.
  - 📜 **C's line says `explicit_mods 0x00`.** The ctrl shows up in the report's modifier byte (`Modifiers set to 0x01`), not in the event field.
- ⚠️ **New finding, not predicted.** When an `htm` is released after a HOLD, `LCTRL` is released twice and ZMK logs `<err> zmk: Tried to unregister modifier 0 too often`. The cause is `hold-while-undecided-linger`.

## 📋 Spec (CLAIMS.md, quoted)

> **T-19 `htm` mechanics** — R1, layer 4 forced via `&mo 4` on pos 3 for the test. Tap: `PRESS(1,1,50) RELEASE(1,1,10) PRESS(0,2,200) RELEASE(0,2,300)`: `kp_pressed 0xE0` at press, no `kp_released 0xE0` at tap end (sticky takes over, count 2→1), C pressed with `explicit_mods 0x01`, `kp_released 0xE0` after C's up. Hold ≥ 130 or key-up after a captured key: captured keys delivered with the mod down. […] the mod is never absent between press and consumption.

## 🖥️ Board translation (nRF52840; per MODEL header and §(a))

- ⏱️ **Remove the native +1 ms from every timer.**
  - Combo rungs: t+16 / t+18 on the board (native t+17 / t+19).
  - `htm` HOLD timer: T+130+δ (native T+131).
  - Sticky expiry: T+1500+δ (native T+1501). δ ∈ (0.03, 1.05] ms.
  - The hold-tap term and the sticky 1500 both count from the original press timestamp on the board too. Only the timer overshoot differs.
- 🧩 **The combo delay before `0xE0↓` depends on position on the real `l_mod` (26).**
  - This is INFERRED from the D-config §6.2 layer lists and not executed here. Only `l_all` combos are live on layer 26, and the hack (0–24) is not.
  - Delayed **16 ms**: `LM1` (`entr`) and `RM1` (`entr2`).
  - Pressed at once (0 ms): `LM4 LM3 LM2 RM2 RM3 RM4`. `wispr`, `bspc`, `del`, `delWord` and `capsWord` are not on 26.
  - The R1 rig's 18 ms (S16 + Q18 on pos 5) is a rig artefact, not a real-keymap number.
- 🔁 **Same logic on the board (same code, no native dependency):**
  - The captured-key path: the hold-tap captures first; on decision the key re-enters the combo engine with its old timestamp and fires immediately.
  - The combo re-capture that orders `skm`'s release before C.
  - The double `release_hold_binding` `<err>` on HOLD release. It is visible only with USB logging.
- 🖐️ **Transport.** On the board, a left-half `htm` gains 0.5–9 ms of BLE delay before it is stamped on the central, and that stamp is T. Debounce adds about 5 ms to press and release equally. Neither changes the ordering shown here.

## 🧾 Deviations (as facts)

1. **T-19-a:** `hid_listener_keycode_pressed … keycode 0xE0` is logged at `[00:00:00.081,000]`, which is **t+19** (hold-tap creation after the rig's 18 ms S16/Q18 combo hold, +1). The spec says "at press" (t+0).
2. **T-19-a:** at tap end (t+51, `[00:00:00.113,000]`), a `hid_listener_keycode_released … keycode 0xE0` line **is logged** (snapshot: `kp_released: … keycode 0xE0`), with `Modifier 0 count: 1` / `Modifiers set to 0x01`. The spec predicted no such line. The modifier byte does not drop, which matches the spec's parenthetical "count 2→1".
3. **T-19-a:** C's press line reads `explicit_mods 0x00` (`[00:00:00.141,000]`). The spec predicted `explicit_mods 0x01`. Ctrl is carried by the report's modifier byte (`Modifiers set to 0x01`, same ms).
4. **T-19-b (unpredicted):** after a HOLD, the `htm` key-up releases `LCTRL` twice at t+163 (`[00:00:00.225,000]`), and the second release logs `<err> zmk: Tried to unregister modifier 0 too often`.
5. **T-19-d (precision on MODEL):** the sticky mod from a tap expires at **t+1501** (`[00:00:01.563,000]`), which is 1500 ms (+1 native) after the `htm` **press**, i.e. 1450 ms after its key-up.

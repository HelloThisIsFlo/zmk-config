## 📜 Spec (CLAIMS.md, quoted)

> **T-10 Late-deadline stall (3-key combo out of order)** — R1, hack on. `PRESS(1,0,11) PRESS(1,2,3) PRESS(1,1,100) RELEASE(1,0,10) RELEASE(1,1,10) RELEASE(1,2,300)` (E t, G t+12, F t+16). Expect `remaining_candidates=… ` at `[t+12]` leaving Q18 only, **no** `filter_timed_out` line at `t+19`, `kp_pressed 0x1A` (W = Q18) only at `[t+117]` (E's release), press stamped `t`. Control: order E, F, G within 11 ms → W at `t+19`. Purpose: R10.

> MODEL R10: *While the timer is DELAYED, `k_work_schedule` is a no-op, so if a 2nd key filters out the shortest candidate the later MIN is never armed; the old timer fires, `:473` early-returns without re-arming → stall until the next event. Example on Flo's board: RM1 then RM3 at +12 ms then RM2 → `delWord` fires only on the first release.*

- **Mock coordinates, keycodes and times agree with RIG.md.** No correction was needed.
  - `(1,0)` = pos 4 E, `(1,1)` = pos 5 F, `(1,2)` = pos 6 G; Q18 = `<4 5 6>` 18 ms `&bk W` (0x1A).
  - The first event has `ms = 11`, so t = 12 abs. G lands at 12 + 11 + 1 = t+12, F at t+16 and E↑ at t+117, exactly as the spec says. The spec already applied the doubled-first-delay rule.
- **Correction to the spec's model (not to its numbers):** the Q18-only state after G is a single candidate, and a single candidate fires on completion (`combo.c:442-446`).
  - A stall at completion needs ≥ 2 live candidates. Flo's real example has them (delWord + capsWord); stock R1 has only Q18.
  - Cases e and f add a 4-key 18 ms sibling to reproduce that.
- **Two cases added beyond the spec: c and d.** They isolate R10 from combo completion, using held keys and no third key.

## 🧠 Why (source trace, `app/src/combo.c`, Zephyr `kernel/work.c:966-969`)

- E↓ at t: candidates S16 (t+16), Q18 (t+18), hack (t+11). MIN is t+11, so the timer is armed and fires at t+12 on native.
- **At t+12 the timer runs before G** (it is a tie; see the ordering block in case a). The handler logs `remaining=2 timestamp=t+11`, dropping the hack.
  - `update_timeout_task()` then re-arms for t+16. This is allowed because the item is only `RUNNING` (`work.c:967` masks out `K_WORK_RUNNING`), and it records `timeout_task_timeout_at = t+16`.
- **G↓ at t+12:** the time filter logs `remaining=2 timestamp=t+12`, and the position filter keeps Q18 (plus X18 in e/f).
  - `update_timeout_task()` wants t+18. `k_work_schedule` returns 0 without scheduling because the item is `DELAYED`, and `:417-418` still records `timeout_task_timeout_at = t+18` (a phantom deadline).
- **t+17:** the real timer fires. `k_uptime_get()` (t+17) is below t+18, so `:473-475` returns early. It logs nothing and re-arms nothing. **From here on there is no timer** (R10).
- Only the next position event can end this state:
  - a (F↓): 1 candidate, now complete, so it fires.
  - e (F↓): 2 candidates, so F only marks Q18 as complete (`:448-452`); then E↑ runs `cleanup()`, which fires Q18.
  - c (E↑): `cleanup()` flushes E and G.

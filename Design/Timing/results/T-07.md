### Why the tie resolves to HIT on native (mechanism, from the log + source)

- Both deadlines are `t+10`: the mock's `k_work_schedule(&data->work, K_MSEC(10))` is called at `t` **inside the mock handler**, the behaviour queue's `k_work_schedule(&queue_work, K_MSEC(10))` later in the same ms (inside the msgq-processor work that delivered B). Zephyr inserts a new timeout only before a *strictly later* one (`zephyr/kernel/timeout.c:126-128`) → equal deadlines stay FIFO → **mock timeout expires first** — matches line ① being first.
- Each expiring delayable submits its work item FIFO (`work.c:810-828` → `submit_to_queue_locked` → `sys_slist_append`, `work.c:277`). So at `t+11` the sysworkq holds `[mock handler, behaviour-queue work]` in that order.
- The mock handler does **not** deliver the key: `zmk_physical_layout_kscan_callback` (`physical_layouts.c:147-160`) does `k_msgq_put` + `k_work_submit(&msg_processor.work)` → the position event is a **third** work item, appended **after** the behaviour-queue work.
- Hence ② (`layer 2 state 1`) runs before ③ (`Row: 0, col: 3 … pressed: true`) — the keymap sees layer 2 already on. The spec's "mock-timer-first → D" assumed the mock handler delivers the position event synchronously; it does not.

The board's genuine TIE cell is **Δ = 10** (key 2 at T+10 vs layer at T+10+δ); native cannot reproduce it (its Δ = 10 is a clean MISS: layer at T+11), and δ's sub-ms phase is not observable here — MODEL's "sub-ms coin flip" stands, but this run shows that *whenever the two timers land in the same workqueue pass with the queue timer already submitted, the layer wins* (workqueue FIFO + msgq hop), which biases the coin toward HIT.
- The 1 ms `+1` native offset on the sticky release (`t+112` vs board `T+110+δ`) and on Q's `kp↑` (`+11` vs `+10+δ`) are the usual timer offsets; nothing else differs structurally.

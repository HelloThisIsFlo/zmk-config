### 🧵 How the nesting shows in the log (all at `[.102]`)

1. The hold-tap presses `ak_R_macro`. Its `queue_macro … count: 1` queues `&ak↓`, and **loop A** starts (it is outside the queue work).
2. Loop A invokes `&ak↓`. Inside it, `&ak`'s `queue_macro … count: 7` queues `kp H↓`. The queue work is not pending, so a **nested loop B** starts.
3. Loop B runs `kp H↓` → HID ↓, then `Processing next queued behavior in 10ms`. That schedules the queue work and loop B breaks.
4. Back inside `&ak`'s `queue_macro`: `tap time set: 0`, `param: 1to1`, and the rest of its items are queued (the work is now pending, so nothing runs yet).
5. Loop A's own `Processing next queued behavior in 0ms` line appears. It keeps draining the FIFO:
   - `kp H↑` → HID ↑
   - `aksl 3↓` → `layer 3 state 1`
   - `aksl 3↑` → arms the 100 ms sticky timer
6. `ak_R_macro`'s `queue_macro` finishes: `&ak↑` is queued (wait 0), but the 10 ms work is pending so it is **not** run. Then the hold-tap release runs (`starting: 1, count: 0`) and `cleaning up hold-tap`.
7. At `[.113]` (t+62) the 10 ms work runs the leftover `&ak↑`. It does nothing (`starting: 7, count: 0`: `&ak` has no release phase).

## 🔌 Board translation (nRF52840)

- **Native offsets removed:**
  - the hack rung and hold-tap creation happen at T+11+δ (δ ≈ 0.03–1.05 ms, MODEL (a)), not T+12
  - the tap decision is driven by the key-up event, not a timer, so it happens at the up's own timestamp (no +1)
  - layer off at T_up + 100 + δ (native: T_up + 101)
  - the leftover no-op `&ak↑` at T_up + 10 + δ
- **Same on the board (it's code structure, not timing):**
  - H↓, H↑ and `aksl↓` (layer ON) run back-to-back in **one** `k_sys_work_q` handler (the hold-tap key-up handler), µs apart with no tick between
  - the nesting (`bq:61-63`, `k_work_delayable_is_pending` false outside the work item) doesn't depend on the tick rate
- **Physical time for Flo's LH0:**
  - LH0 is on the **left half (peripheral)**, so T_up = the BLE receipt of the release at the central (+4–6 ms debounce, +0.5–9 ms to the next 7.5 ms anchor; MODEL (a))
  - the "r" appears at thumb-release receipt, and l_akR is live right away. There is no +10 ms layer delay as with every other `&ak`.
- **Host-drop risk (the purpose of this test)**
  - **What native proves:** two separate HID reports, press then release (two `zmk_endpoints_send_report: usage page 0x07` lines at `[00:00:00.102,000]`). Neither is merged or lost inside ZMK.
  - **Beyond that, source reading only (not observed):**
    - USB: `usb_hid.c:139` `k_sem_take(&hid_sem, K_MSEC(30))` runs before every `hid_int_ep_write`, and the sem is given back in `in_ready_cb` (`:27`). So the release report can't go out until the host has polled the press report: they are at least one host poll apart.
    - BLE: both reports are `k_msgq_put` into `zmk_hog_keyboard_msgq` (`hog.c:259`) and drained by `hog_keyboard_work` as two separate `bt_gatt_notify_cb` calls (`:233-245`). INFERRED: they can land in the same connection event.
  - **Can't be settled natively:** whether the host OS registers a down/up pair that arrives with ~0 spacing. That needs hardware, in the style of T-24.

## 🏁 Verdict: `as_predicted`

- **Deviations:** none. Every spec time was observed exactly:
  - H↓ `[00:00:00.102,000]` = t+51
  - H↑ `[00:00:00.102,000]` = t+51
  - `layer 3 state 1` `[00:00:00.102,000]` = t+51
  - `layer 3 state 0` `[00:00:00.203,000]` = t+152
- **Facts beyond the spec (not deviations):**
  - A `Processing next queued behavior in 10ms` line (from nested loop B) sits between the H↓ and H↑ lines, both in the log and in the snapshot. H↑ is still emitted in the same ms, by loop A.
  - The 10 ms tick that loop B scheduled fires at t+62 (`[00:00:00.113,000]`). It only runs `ak_R_macro`'s leftover `&ak` release, which does nothing (`starting: 7, count: 0`).
  - Control (b): without the wrapper macro, H↑ and the layer come at t+62 (`[00:00:00.113,000]`) and the layer goes off at t+163 (`[00:00:00.214,000]`). This shows the 0 ms tap comes from the wrapper macro.

- **MODEL.md (c) "R thumb" bullet:** INFERRED can become **PROVEN on native** (0 ms tap, layer ON at the decision instant). Whether the host keeps a 0 ms tap stays hardware-only.
